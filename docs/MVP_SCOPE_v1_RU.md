# Micro Shop — MVP Scope v1 (РФ)

**Версия:** 1.0  
**Дата:** 2026-08-13  
**Рынок:** Российская Федерация  
**Статус:** рабочий документ для команды и подрядчиков  

---

## 1. Назначение документа

Документ фиксирует **границы первой версии продукта (MVP)** для рынка РФ: что строим, что сознательно откладываем, и по каким критериям считаем MVP готовым.

MVP — это **не** полная платформа из инвесторской презентации и **не** серийное производство. Это **одна рабочая установка**, на которой подтверждается ключевой пользовательский цикл:

> **Регистрация → вход в сессию → взятие товара → мгновенная оплата → фискальный чек**  
> Целевое время: **60–120 секунд**.

После MVP возможны: демо для партнёров, внутренние испытания, подготовка к пилотной локации. Инвестиционная упаковка и масштабирование сети — **за пределами** этого scope.

## 3. Definition of Done — MVP готов, когда

### 3.1. Пользовательский сценарий

- [ ] Покупатель регистрируется в мобильном приложении и привязывает способ оплаты.
- [ ] Покупатель открывает сессию на тестовой точке (QR / NFC / код).
- [ ] Покупатель берёт товар из шкафа; **оплата происходит в момент взятия**, до закрытия двери.
- [ ] Фискальный чек приходит в приложение и/или на email **≤ 5 секунд** после списания.
- [ ] Сценарий работает для **всех трёх категорий**: овощ, молоко, горячее блюдо.
- [ ] Среднее время покупки **≤ 120 секунд** (замер на ≥ 20 тестовых пользователях).

### 3.2. Техническая надёжность

- [ ] ≥ **100 успешных транзакций** подряд на lab-стенде без критических сбоев.
- [ ] Точность идентификации товара и суммы списания **≥ 99%**.
- [ ] Холодильный модуль держит **+2…+6 °C** непрерывно ≥ 24 ч.
- [ ] Индукционный модуль: безопасный нагрев, аварийное отключение, контроль температуры блюда.
- [ ] Edge-контроллер переживает кратковременный offline (≥ 30 сек) с буферизацией событий.
- [ ] Uptime edge-контроллера **≥ 95%** за 7 суток непрерывной работы.

### 3.3. Юридическая готовность (РФ)

- [ ] Онлайн-касса и ОФД подключены; чеки соответствуют **54-ФЗ**.
- [ ] Момент расчёта = момент выдачи товара (модель «оплата при взятии»).
- [ ] Обработка персональных данных — в соответствии с **152-ФЗ** (минимальный compliance).
- [ ] Договорная база для тестовой площадки (аренда места / внутренняя lab-площадка).

### 3.4. Артефакты по итогам MVP

- [ ] 1 физическая установка (lab / demo).
- [ ] Документация: ТЗ as-built, BOM v1, схемы подключения.
- [ ] Рабочие: mobile app (минимум 1 платформа), backend, edge firmware.
- [ ] Отчёт испытаний: метрики времени, точности, температуры, сбоев.
- [ ] Видео demo end-to-end (3–5 мин) для партнёров.

## 4. Границы MVP — что входит

### 4.1. Физическая установка

| Элемент | Scope MVP |
|---|---|
| Количество модулей | **1 ведущий + 2 ведомых** (итого 3 шкафа), не полный комплект 6–8 |
| Модуль «Овощ» | 1 шкаф: бункер/выдача, весовой контур, базовая станция выдачи |
| Модуль «Молоко» | 1 шкаф: охлаждение +2…+6 °C, полки под SKU молочной категории |
| Модуль «Рис с разогревом» | 1 шкаф: хранение готовой еды + **индукционный нагрев по запросу** |
| Связь модулей | Master/slave, vertical bus — **упрощённая реализация**, достаточная для 3 модулей |
| Сенсоры MVP | Вес (тензоячейка), температура, состояние двери/замка; камера — **опционально** |
| Корпус | Функциональный прототип (v0/v1); промышленный дизайн серии — **не MVP** |
| ИБП | Базовый — для контроллера и критичных узлов (холодильник) |
| Место установки | **1 lab / demo площадка** в РФ (офис, склад, технопарк — не коммерческий трафик) |

### 4.2. Идентификация товара (MVP)

**Выбранный подход для v1:** **весовая идентификация SKU** (1 SKU — 1 ячейка / 1 полка / 1 бункер).

- Каждый слот привязан к конкретному SKU с известной tare и допустимым диапазоном веса.
- При взятии товара фиксируется delta веса → определяется SKU → сумма → списание.

**Не в MVP:** универсальный vision-AI, свободный выбор из смешанного шкафа без привязки слота.

### 4.3. Edge-контроллер (firmware)

| Функция | MVP |
|---|---|
| Управление замками и сессией | ✓ |
| Чтение веса, температуры, двери | ✓ |
| Событие «товар взят» → триггер оплаты | ✓ |
| Связь с облаком (REST/MQTT) | ✓ |
| Offline-буфер событий | ✓ |
| OTA-обновления | ✓ (базово) |
| Управление индукцией | ✓ |
| Локальный UI на шкафу | ✗ (только app) |

### 4.4. Backend (SaaS)

| Функция | MVP |
|---|---|
| Регистрация / auth (телефон + SMS или email) | ✓ |
| Профиль пользователя, привязка карты | ✓ |
| Каталог SKU (≤ 30 позиций на 3 сценария) | ✓ |
| Управление остатками (ручное + по событиям веса) | ✓ |
| Сессии покупки | ✓ |
| Транзакции и статусы оплаты | ✓ |
| API для edge-контроллера | ✓ |
| Админка оператора (1 локация) | ✓ |
| Фискализация (интеграция с ОФД через провайдера) | ✓ |
| Мультипоставщики, split payments | ✗ |
| ИИ-ценообразование | ✗ |
| Рейтинг поставщиков | ✗ |
| Резервирование товара | ✗ |
| Удалённая выдача | ✗ |
| Цифровой двойник / advanced analytics | ✗ |

### 4.5. Mobile app

| Функция | MVP |
|---|---|
| Регистрация, вход | ✓ |
| Привязка банковской карты (через платёжного провайдера) | ✓ |
| Скан QR / NFC для старта сессии | ✓ |
| Push / экран «идёт покупка» | ✓ |
| История покупок | ✓ |
| Чек (in-app + email) | ✓ |
| Обратная связь / жалобы (PPA №9) | ✗ |
| Кабинет поставщика | ✗ |
| iOS + Android | **Минимум 1 платформа** (вторую — сразу после MVP или cross-platform) |

**Рекомендация v1:** Flutter или React Native — одна кодовая база под обе платформы; если ресурс один — Android first (проще sideload на demo).

### 4.6. Операционная модель MVP

| Роль | MVP |
|---|---|
| Оператор сети | **1 юрлицо** (вы) |
| Поставщик | **1 поставщик** (может быть то же юрлицо) |
| Владелец локации | Lab-площадка (своё помещение или договор) |
| Покупатель | Тестовые пользователи + сотрудники + invited beta |

Платформенная экономика (слоты, аренда полок, несколько поставщиков) — **после MVP**.

### 4.7. Платежи и фискализация (РФ)

| Требование | MVP |
|---|---|
| Эквайринг (списание с карты) | ✓ через провайдера (ЮKassa, CloudPayments, Т-Банк и т.п.) |
| Онлайн-касса + ОФД | ✓ |
| Момент расчёта при выдаче товара | ✓ |
| Email / in-app чек | ✓ |
| СБП | ○ желательно, не блокер v1 |
| Хранение PAN на своих серверах | ✗ только tokenization у провайдера |

### 4.8. Регуляторика и compliance (РФ, MVP-minimum)

| Область | MVP |
|---|---|
| 54-ФЗ (онлайн-кассы) | ✓ обязательно |
| 152-ФЗ (ПДн) | ✓ политика, согласие, минимальный набор данных |
| Требования к торговле продовольствием | ✓ базовые условия хранения (температура, сроки) |
| EAC / сертификация оборудования | ○ для lab — не блокер; для публичного пилота — отдельный трек |
| Биометрия (152-ФЗ, отдельные требования) | ✗ не в MVP |
| Маркировка «Честный ЗНАК» | ○ зависит от SKU; для MVP выбрать **немаркированные** или упрощённые категории |

## 6. Товарные сценарии MVP — детализация

### 6.1. «Овощ»

| Параметр | MVP |
|---|---|
| Формат | Свежие овощи/фрукты в фасовке или насыпью (1–3 SKU) |
| Выдача | Бункер или выдвижной лоток + весовой контроль |
| Маркировка | Без «Честного ЗНАКа» на MVP-SKU |
| Контроль качества | Ручной отбор; автоматика — только вес и факт выдачи |
| Целевой SKU count | 3–5 позиций |

### 6.2. «Молоко»

| Параметр | MVP |
|---|---|
| Формат | Упакованная молочная продукция (молоко, кефир, творог) |
| Температура | +2…+6 °C, логирование каждые 5 мин |
| Идентификация | 1 SKU = 1 полка / слот, вес ± допуск |
| Целевой SKU count | 5–10 позиций |

### 6.3. «Рис с разогревом»

| Параметр | MVP |
|---|---|
| Формат | Готовое блюдо в контейнере (1–2 SKU) |
| Хранение | Охлаждённое или controlled ambient — по рецептуре SKU |
| Нагрев | Индукция **по явному запросу** в app после взятия контейнера |
| Безопасность | Таймаут, контроль температуры, блокировка при ошибке датчика |
| Целевой SKU count | 1–2 позиции |

**Общий лимит каталога MVP:** ≤ **30 SKU** суммарно.

## 10. Решения, требующие подтверждения (checklist)

Перед стартом F1 зафиксировать:

- [ ] **Юрлицо для MVP** — на каком ООО/ИП идут платежи и касса
- [ ] **Lab-площадка** — адрес, электричество (220V, отдельные линии на холод + индукцию)
- [ ] **Платёжный провайдер + касса** — выбранный вендор
- [ ] **Mobile: одна или две платформы** на v1
- [ ] **Идентификация: только вес** — подтверждено (рекомендация документа)
- [ ] **SKU-лист MVP** — черновик 15–30 позиций
- [ ] **Hardware подрядчик** — найден или in-house
- [ ] **Бюджет MVP** — верхняя граница утверждена
